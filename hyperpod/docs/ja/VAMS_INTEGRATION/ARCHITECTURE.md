# VAMS 連携の仕組み

VAMS（Visual Asset Management System）のワークフローから、PASK の HyperPod クラスタで LeRobot（pi0 と pi0.5）の学習を実行する連携の、仕組みと制約をまとめます。
読者は、VAMS から学習を実行する利用者と、連携を運用または改修する開発者です。
導入の手順と設定項目の一覧は [VAMS 連携の導入と運用](/hyperpod/docs/ja/VAMS_INTEGRATION/OVERVIEW.md)、メッセージやファイルの形の詳細は [VAMS 連携の仕様](/hyperpod/docs/ja/VAMS_INTEGRATION/SPEC.md) にあります。

## 連携の範囲

VAMS の利用者は、LeRobot v3.0 のデータセットのアセットを選んでワークフローを実行し、学習済みモデルを別のアセットとして受け取ります。
学習の経過と結果は、PASK の MLflow App の experiment `vams-training` に記録されます。

連携の機能はすべて PASK 側にあり、VAMS のコードとデプロイの設定は変更しません。
VAMS には、PASK に同梱するパイプラインとワークフローの定義（`hyperpod/vams/`）を登録するだけです。
VAMS と PASK が同じ AWS アカウントの同じリージョンにあることを前提にします。
アカウントやリージョンを分ける構成と、1 週間を超える学習は対象外です。

## 全体の流れ

VAMS は、組み込みの SQS 実行タイプ（`waitForCallback=Enabled`）のパイプラインとして PASK を呼び出します。
PASK の login ノードに常駐するポーラー（systemd のサービス `pask-vams-poller`）が、実行を次の順に進めます。

1. VAMS の Step Functions が、PASK の SQS キューにメッセージを送り、TaskToken が返るまで待ちます。
2. ポーラーはメッセージを受け取り、実行を PASK の DynamoDB に記録してから、メッセージを削除します。
3. ポーラーは、VAMS のアセットバケットから PASK のデータバケットの `vams/<pipelineExecutionId>/` へ、入力のデータセットをコピーします。
   入力が curation のビューの場合は、ビューが指す元のアセットのファイルをコピーします（「curation のビューの解決の流れ」の節）。
   コピーしたファイルは、FSx for Lustre の自動取り込みで `/fsx/s3link/vams/<pipelineExecutionId>/` に現れます。
4. ポーラーは `slurm_train.sh` を Slurm のジョブとして投入し、ジョブが終わるまで監視します。
5. ジョブが成功すると、ポーラーは学習済みモデルを VAMS の outputs に書き戻し、`SendTaskSuccess` を返します。
   VAMS は outputs のファイルを出力のアセットに取り込みます。
6. ポーラーは、PASK のデータバケットのコピーと、FSx の実行ディレクトリと出力ディレクトリを削除します。

実行の状態は、VAMS と PASK で持ち主が分かれます。
ワークフローとステップの状態（実行中、成功、失敗、中断）は VAMS が持ち、PASK は `SendTask*` を返すだけです。
Slurm のジョブ ID、TaskToken、PASK 側のパスは、PASK の DynamoDB が持ちます。
PASK が自分で記録するのは、hyperpod スタックに slurmdbd が無く、終わったジョブが数分で `squeue` から消えるためです。

## 利用者が指定するものと受け取るもの

利用者は、VAMS でワークフロー `pask-lerobot-openpi-training` を実行するときに、次のものを指定します。

| 指定するもの | 内容 |
|---|---|
| 入力（通常のデータセット） | データセットのアセット全体。LeRobot v3.0 のデータセットがアセットのルートにあり、ルートに `meta/info.json` がある必要があります |
| 入力（curation のビュー） | VAMS の LeRobot Dataset Curation が作ったビューのアセット全体。ルートに `curation_manifest.json` があり、その `mode` が `view` である必要があります。ビューと元のアセットは同じデータベースに置きます |
| 出力のアセット | 学習済みモデルを入れるアセット。データセットとは別のアセットにします |
| 学習パラメータ | `POLICY_TYPE`、`FINETUNE_MODE`、`STEPS`、`SAVE_FREQ` など、テンプレートのタグにある項目だけ。許可リストに無いキーがあると実行は失敗します |

どちらの入力でも、ファイルを 1 つだけ選ぶ指定と、アセット内のフォルダを選ぶ指定は受け付けません。

実行が成功すると、利用者は次のものを受け取ります。

- 出力のアセットに、`checkpoints/last/pretrained_model` 配下のファイル（重み、設定、前処理と後処理の設定）が入ります。optimizer の状態は入りません。
- VAMS の実行の詳細の results に、`pask_training.json`（Slurm のジョブ ID、学習パラメータ、dataset digest、MLflow の run ID、入力の種類）が入ります。ビューの場合は、元のアセットと残したエピソードの数も入ります。
- MLflow の run に、`pask.trigger=vams` と `vams.*` のタグ（VAMS の実行 ID、入力と出力のアセットなど）、入力のデータセット、入力のファイル一覧（artifact `vams/input_manifest.json`）が記録されます。ビューの場合は、元のアセットのタグ、ビューのマニフェスト（artifact `vams/curation_manifest.json`）、学習に使った正規化統計（artifact `vams/norm_stats.json`）も記録されます。

VAMS で実行を中断すると、ポーラーは中断を検知してジョブを `scancel` します。
VAMS からの中断の通知は無いので、ポーラーは heartbeat が TaskToken の失効のエラーを返したことで中断を検知します。
VAMS の送信のリトライでは新しい TaskToken が届くことがあるため、ポーラーは猶予（既定 30 分）を待ってから中断と判断します。

失敗したときは、VAMS の実行の詳細に次のエラー名が表示されます。

| エラー名 | 原因 |
|---|---|
| `PASK.InvalidRequest` | 入力の指定、または学習パラメータが条件に合いません。入力については次の場合です。ルートに `meta/info.json` も `curation_manifest.json` も無い。`curation_manifest_version` が 2 以外。ビューのマニフェストが不正（必須の項目が無い、エピソードの番号が不正など）。マニフェストが別のデータベースかバケットを指している。マニフェストが記録した版が元のアセットに無いか、サイズが記録と違う |
| `PASK.StagingFailed` | データのコピーに失敗したか、FSx の空きが足りないか、取り込みが待ちの上限（既定 3600 秒）までに終わりませんでした。ビューの場合は、ポーラーが元のアセットを読めない（403）場合も含みます |
| `PASK.SubmitFailed`、`PASK.JobLost` | ジョブを投入できなかったか、ジョブの終了を確認できませんでした |
| `PASK.JobFailed` | 学習のジョブが失敗しました。ビューの正規化統計の計算の失敗も含みます |
| `PASK.OutputUploadFailed` | 学習済みモデルを outputs に書き戻せませんでした |

## データを VAMS のバケットから分けてコピーする理由

学習の入力は、VAMS のアセットバケットを FSx に直接つながず、実行ごとに PASK のデータバケットへコピーします。
同じ S3 のデータを VAMS と FSx の両方が同期すると、ファイルの中身と VAMS の版の記録が食い違い、データが破損する可能性があるためです。

PASK の FSx は、データバケットとのあいだにデータリポジトリの関連付けを持ち、作成、変更、削除のすべてを双方向に自動で反映します。
VAMS のアセットバケットをこの関連付けでつなぐと、次の 2 つの場合に VAMS のデータと記録が食い違います。

- FSx 上でファイルを書き換えると（たとえば学習の前処理で `meta/stats.json` を作り直すと）、その変更が VAMS のバケットに自動で書き出されます。VAMS は自分の API を通らない変更を版として記録しないので、VAMS が管理するアセットの版と S3 の中身が一致しなくなります。FSx 上での削除も VAMS の元データの削除になります。
- 学習の途中で VAMS 側でアセットを更新すると、その変更が FSx に取り込まれます。学習のジョブは、読み込みの途中で別の版のファイルに切り替わったデータを読むことになります。

このほか、FSx の自動取り込みは対象のバケットに S3 のイベント通知を設定するので、VAMS がアセットバケットに設定する通知と重なります。

コピーでは、入力を一覧にした時点の VersionId を指定してコピーします。
そのため、実行中に VAMS でアセットが更新されても、学習は一覧にした時点の版を読みます。
コピー先は実行ごとに分かれ、実行が終わると削除されるので、PASK 側の変更が VAMS のデータに及ぶことはありません。
ポーラーには VAMS のバケットの削除の権限を付けていません。

Mountpoint for Amazon S3 などで VAMS のアセットバケットを各ノードに直接マウントし、コピーせずに読む方式も採りません。
この方式では、学習のジョブはアセットバケットにある最新の版を読みます。Mountpoint for Amazon S3 は版を指定して読めないからです。
学習は数時間から数日続きます。そのあいだに VAMS でアセットが更新、削除されると、ジョブは学習の途中から別の版のデータを読むので、データの不整合が起きる可能性があります。
読み取り専用でマウントしても、この問題は残ります。
防ぐには、版の固定や、学習の前後での入力の変化の検出など、さまざまな考慮が必要になります。
そのため現時点では、実行した時点のデータをコピーし、そのコピーを学習のあいだ固定して使います。

## curation のビューの解決の流れ

VAMS の LeRobot Dataset Curation のビュー方式は、エピソードを選んだ結果を、データをコピーせずにビューのアセットとして残します。
ビューのアセットにあるのは、`curation_manifest.json` と、残したエピソードで計算した `meta/stats.json` だけです。
data と動画は元のアセットに残ったままで、マニフェストが元のファイルを S3 の版（VersionId）で指します。
PASK は、このマニフェストから元のファイルを解決して学習します。
VAMS から PASK へのメッセージの形は、通常のデータセットと同じです。

ポーラーと学習ジョブは、次の順にビューを解決します。

1. STAGING で、ポーラーは入力のアセットのルートの最新版を一覧にします。ルートに `curation_manifest.json` があれば、一覧にした版を読みます。`mode` が `view` ならビューとして扱い、マニフェストを検証します。
2. ポーラーは、マニフェストの `source.files` の各ファイルに、記録された版（VersionId）を指定して `HeadObject` を行い、版があることとサイズが記録と同じことを確かめます。版が無ければ、理由を付けて実行を失敗にします。
3. ポーラーは、記録された版を実行ごとのバケット（PASK のデータバケットのステージング prefix）にコピーします。ビュー自身のファイルはコピーしません。版を指定してコピーするので、ビューを作った後に元のアセットが更新されても、学習はビューを作った時点の版を読みます。
4. 取り込みが終わると、ポーラーは実行ディレクトリにマニフェストを `curation_manifest.json` として書き、学習に使うデータセットのルート `view_dataset/` を作ります。`view_dataset/meta/` は実ディレクトリで、その下の各ファイルと、ルート直下の `data` と `videos` などは、FSx に取り込まれたファイルへのシンボリックリンクです。FSx に取り込まれたファイルは root の所有で学習ジョブが書き込めないので、学習ジョブが `meta/stats.json` を書ける場所を実行ディレクトリに用意します。
5. 学習ジョブは、学習の前に `compute_view_stats.py` で、残すエピソードの正規化統計を計算し、`view_dataset/meta/stats.json` に書きます。数値の特徴量（`observation.state`、`action` など）は、残すエピソードの行から LeRobot の `get_feature_stats` で計算します。画像と動画の特徴量は、`meta/episodes` にあるエピソードごとの統計を LeRobot の `aggregate_stats` でまとめます。
6. `mlflow_train.py` は、マニフェストの `episodes` を `--dataset.episodes` として `lerobot-train` に渡します。エピソードの番号は、元のデータセットの `episode_index` のままです。

学習ジョブが正規化統計を計算し直すのは、LeRobot 0.6.1 の `lerobot-train` が、エピソードを指定しても `meta/stats.json` をそのまま正規化に使うためです。
ビューの `meta/stats.json` は表示と参考のための値として扱い、学習には使いません。
LeRobot の `lerobot-edit-dataset` の統計の再計算も使いません。
LeRobot v3.0 の data のファイルは複数のエピソードの行を持つので、この再計算は、同じファイルにある除外したエピソードの行も統計に含めてしまいます。
openpi の `compute_norm_stats` も使いません。
openpi の学習用の `norm_stats.json` を書くもので、PASK の VAMS 連携の学習（LeRobot の `lerobot-train` による pi0 と pi0.5）はこのファイルを読まないためです。

エピソードの一覧を `slurm_train.sh` のコマンドラインに入れず、`mlflow_train.py` がプロセスの中で引数に加えるのは、Linux では 1 つの引数が 128 KiB を超えられないためです。
エピソードが数万あると、`srun` の引数に収まらない可能性があります。

ビューの学習ジョブには、`HF_HUB_OFFLINE=1` を渡しません。
データセットのファイルが足りない場合でも、データセットを Hugging Face Hub から取りにいくことはありません。
ビューのデータセットの `repo_id`（`vams/<databaseId>/<assetId>`）は 3 つに区切られているので、`huggingface_hub` が Hub への通信の前に `HFValidationError` で止めるためです。
事前学習の重みとトークナイザーは、通常の学習と同じく、クラスタの `LEROBOT_PI_HF_HOME` のキャッシュに無ければ Hub から取得します。

## データの量の目安と、大きくなった場合の代替案

今の実装は、ポーラーが 1 つのプロセスで、オブジェクトごとに S3 のサーバー側のコピーを行います（8 つのオブジェクトを並列にコピーし、5 GiB を超えるオブジェクトはマルチパートでコピーします）。
動作を確かめたのは、約 100 MB、11 ファイルのデータセットです。
1 回の学習のデータが大きくなると、次の理由で、実行が遅れるか失敗する可能性があります。

- コピーにかかる時間は、オブジェクトの数と合計のサイズに比例して伸びます。この時間は、Slurm の待ちと学習の時間とともに、VAMS のパイプラインの `taskTimeout`（同梱の `hyperpod/vams/pipeline.json` では 432000 秒（5 日）、VAMS の上限は 7 日）に含まれます。
- コピーの途中でポーラーが止まると、再開したポーラーはすべてのオブジェクトをコピーし直します。長いコピーの終わり近くで止まると、それまでの時間がそのまま無駄になります。
- ポーラーは実行を 1 件ずつ処理するので、コピーのあいだ、ほかの実行の受付の後の処理が待たされます。
- FSx の自動取り込みはファイルのメタデータだけを取り込み、中身は学習のジョブが最初に読むときに S3 から読み込まれます。データが大きいと、最初のエポックが遅くなります。
- FSx の容量は 1200 GiB で固定です。コピーの前に、データセットの合計とチェックポイントの見込み（`FINETUNE_MODE` が `full` の場合は 1 つあたり約 40 GiB）が空きに収まるかを確かめ、収まらなければ `PASK.StagingFailed` で失敗にします。

1 回の学習の入力が次のどれかに当たる場合は、コピーの方法を見直します。
値は、上の理由から見積もった目安で、測って確かめた値ではありません。

| 見直しの目安 | 理由 |
|---|---|
| 合計 100 GiB を超える | コピーと最初のエポックの読み込みが数十分から数時間になり、途中で止まったときのやり直しが大きくなります |
| オブジェクトが 1 万を超える | オブジェクトごとのコピーと、取り込みの確認（取り込みの済んでいないファイルの有無とサイズを 10 秒ごとに確かめます）が律速になります |
| データセットとチェックポイントの合計が FSx の空き（数百 GiB）に近い | 容量の確認で失敗するか、学習中にチェックポイントを書けなくなります |

見直しの代替案は次のとおりです。
小さな変更で済むものから並べています。

1. データセットのフォルダだけをコピーする: 学習パラメータにアセット内の相対パスを加え、その下だけをコピーします。学習に使わないファイル（元の rosbag など）をコピーしなくなります。
2. コピー済みのオブジェクトを飛ばす: コピー先に同じサイズと ETag のオブジェクトがあればコピーしないようにし、止まった後に続きから再開できるようにします。
3. S3 Batch Operations でコピーする: ポーラーは一覧から manifest を作ってジョブを起動し、完了を監視するだけにします。数百万のオブジェクトまで扱え、リトライと完了レポートを S3 側に任せられます。1 オブジェクトあたりのサイズの上限は、導入の前に確かめる必要があります。
4. AWS DataSync でコピーする: TB 規模のデータで、転送の検証と差分の転送が必要な場合に使います。
5. FSx の読み込みを学習の前に済ませる: コピーの後に `lfs hsm_restore` かデータリポジトリのタスクで中身を読み込み、最初のエポックの遅れを学習の時間から外します。
6. FSx の容量を増やすか、実行ごとに FSx を用意する: データセットとチェックポイントが固定の 1200 GiB に収まらない場合に検討します。

VAMS のアセットバケットを FSx に直接つないでコピーをなくす案は、上の「データを VAMS のバケットから分けてコピーする理由」の問題があるため採りません。

## 権限とセキュリティ

ポーラーは、login ノードのインスタンスのロールで AWS にアクセスします。
作ってあるクラスタでは、HyperPod がインスタンスグループのロールの変更を受け付けないため、`Vams.SeparateLoginRole` を `false` にして、すべてのグループに共通のロールへポーラーの権限を付けます。
login 用のロールを分けられるのは、クラスタを新しく作る場合だけです。

login ノードには、ポーラーのほかに、人も SSH で入ります。
login ノードに SSH した人は、インスタンスのロールを通じて、ポーラーと同じ次の権限を使えます。

- VAMS のアセットバケットの読み取りと、実行用バケットの outputs の prefix（`*pipelines/*/output/*`）への書き込み
- 名前が `vams-` か `*<ConfigName>*` に一致する Step Functions のステートマシンへの `SendTaskSuccess`、`SendTaskFailure`、`SendTaskHeartbeat`
- PASK のキューのメッセージの受信と削除、実行の状態のテーブルの読み書き
- PASK のデータバケットの `<S3Prefix>vams/` の読み書きと削除

login ノードに SSH できる人（login ノードへの `ssm:StartSession` を許可された人）を、これらの権限を持たせてよい人に限ってください。
`SeparateLoginRole` が `true` の場合、controller と worker のノードのロールには、これらの権限はありません。
学習ジョブは worker のノードで動くので、学習のコードから VAMS のバケットにはアクセスできません。

`SeparateLoginRole` が `false` の場合、すべてのグループが共通のロールを使うので、controller と worker のノードと、そこで動く学習のコードも、上の権限を使えます。
クラスタのどのノードに SSH できる人も、上の権限を持たせてよい人に限ってください。

VAMS のどのバケットにも、削除の権限（`s3:DeleteObject`）は付けていません。
ポーラーが削除できるのは、PASK のデータバケットの `<S3Prefix>vams/` の下だけです。

ビューを入力にした実行では、ポーラーは元のアセットのファイルを、記録された版を指定して読みます。
版を指定した読み取りに要る権限は `s3:GetObjectVersion` です。
ポーラーのロールは `Vams.AssetBucketNames` のすべてのバケットにこの権限を持つので、ビューのために IAM を変更する必要はありません。

PASK は、VAMS の権限（Tier 2 の制約など）を判定しません。
ビューと元のアセットが同じデータベースにあり、VAMS の権限が同じ条件で当たることを前提にします。
ビューのマニフェストはビューのアセットのファイルなので、そのアセットに書き込める人は、同じアセットバケットにある別のデータベースのアセットを指すマニフェストを置けます。
ポーラーのロールはアセットバケット全体を読めるので、IAM だけではこの指定を防げません。
そこでポーラーは、マニフェストの `source.storage.bucket` が入力のアセットのバケットと同じで、`source.database_id` が入力のアセットのデータベースと同じことを確かめます。
違えば `PASK.InvalidRequest` で失敗にします。

学習パラメータは許可リストと正規表現で検証し、シェルを通さずに `subprocess` の引数と環境変数で学習ジョブに渡します。
pipelineExecutionId は文字種（`^[A-Za-z0-9_-]+$`）を検証してから、ジョブ名、S3 のキー、FSx のパスに使います。

ポーラーの設定ファイル `/etc/pask/vams-poller.env` は、所有者が root、グループが ubuntu で、権限は 0640 です。
`HF_TOKEN` を持つ学習用の env ファイル `~/.config/pask/lerobot-openpi.env` は、ubuntu だけが読めます（0600）。

## 今の実装の制約

- 同時に処理する実行は 1 件です（`Vams.MaxConcurrentRuns`）。後から来た実行は、先の実行が終わるまで受付の状態で待ちます。
- データセットはアセットのルートに置く必要があります。サブフォルダにデータセットがあるアセットは、そのままでは学習に使えません。
- FSx に取り込まれたファイルは root の所有になり、学習のジョブはデータセットの中に書き込めません。`meta/stats.json` に q01 と q99 が無いデータセットは、分位点の計算ができずに失敗する可能性があります。VAMS の rosbag から LeRobot への変換の出力には q01 と q99 が含まれます。
- 学習済みモデルは、出力のアセットのルートに置かれます。
- ビューは、元のアセットのファイルを記録された版で指します。元のアセットを消すか、記録された版を消すと、そのビューでは学習できなくなります（`PASK.InvalidRequest`）。ビューで学習するあいだは、元のアセットとその版を消さないでください。
- ビューのマニフェストの形は、`curation_manifest_version` 2 の契約に合わせています。VAMS がマニフェストの形を変えた場合は、ポーラーの検証を合わせて直す必要があります。
- ビューで受け付けるのは、LeRobot の `codebase_version` が `v3.0` のデータセットだけです。それ以外の版は、正規化統計の計算で失敗します（`PASK.JobFailed`）。
- ビューのデータセットのファイルが FSx に足りないと、学習はデータセットの読み込みで失敗します（`PASK.JobFailed`）。`repo_id` が 3 つに区切られているので、Hugging Face Hub への通信の前に `HFValidationError` で止まります。
